title: atoms.input: initial solutions that a PASSIVE atom would ignore stop the run

A PASSIVE atom keeps the populations it starts with: LTE, or with `OLD_POPULATIONS` those read from its populations file (`readatom.c`); passive hydrogen takes them from the atmosphere, or LTE with `HYDROGEN_LTE = TRUE` (`distribute_nH`). RH accepted three kinds of input that it then ignored without a message, and the shipped examples used two of them:
- `ZERO_RADIATION` on a passive atom gave LTE populations (the manual, §4.2.1, says so; nothing in the run did). `rhf1d/run` had H, O and He passive with `ZERO_RADIATION`, `rhsc2d/run` and `rhsc3d/run` H, O and Mg, `rhsphere/run` O and Mg.
- A populations file with `LTE_POPULATIONS` (or `ZERO_RADIATION`) on a passive atom was not read: Fe, Mg and Na in `rhf1d/run`, Na in `rhsc2d/run` and `rhsc3d/run`, Fe and Na in `rhsphere/run`, besides the `ZERO_RADIATION` entries above.
- Passive hydrogen with `OLD_POPULATIONS` read the file, and `distribute_nH` then replaced the populations (and leaked the matrix read).

Following the policy that malformed input stops the run, `readAtomicModels` now stops each of these at input (ERROR_LEVEL_2), with a message that says what to use instead: `LTE_POPULATIONS`, or `OLD_POPULATIONS` with a file of populations to read (for hydrogen: `LTE_POPULATIONS`, or hydrogen ACTIVE). Still valid: a passive atom with `LTE_POPULATIONS` and no file, a passive atom other than hydrogen with `OLD_POPULATIONS` and a file (the way to give a passive atom non-LTE populations, e.g. from an earlier run with the atom active), and every initial solution of an ACTIVE atom, with or without a file (a file is read with `OLD_POPULATIONS` or `STARTING_J = OLD_J`). The example `atoms.input` of the four geometries now give every passive atom `LTE_POPULATIONS` without a file, which is what they got. `tests/run_tests.sh` (`@H6_ACTIVE`, which made H_6 active by replacing PASSIVE) now writes the whole entry, `ACTIVE ZERO_RADIATION pops.H.out`, as before; `tests/run_stress.sh`, which makes the other active atoms passive, writes `PASSIVE LTE_POPULATIONS` for them.

How much it mattered: on FAL-C (`rhf1d/run`, modernize c204d76, 1 thread) He passive with `ZERO_RADIATION` and with `LTE_POPULATIONS` give byte-identical `background.dat`, `spectrum.out` and `atmos.out`; He passive with `OLD_POPULATIONS` read from a run with He active changes I at mu = 0.953 by up to 60 % at 30-65 nm (He I and He II continua) and by at most 7e-5 from 120 to 400 nm, nothing above. So nobody who used the examples was misled about results above 120 nm; below, the populations they believed non-LTE were LTE.

Measured (evidence: `/hao/solar1/dwijn/claude/RH/evidence/b59-passive/`, README): the example inputs of all four geometries before (on a build of c204d76) and after (on this branch), N_MAX_ITER = 4, 1 thread: `spectrum.out` and `J.dat` byte-identical; the `@H6_ACTIVE` entry of `run_tests.sh` is the same text as before. `run_tests.sh --exact` against a build of c204d76: all 38 checks pass, the 12 comparisons with the baseline byte-identical (both builds run the new example inputs).

Tests: `tests/e2e/passive_atoms.py` (new, 9 checks): passive He with `ZERO_RADIATION` (without and with a file), passive He with `LTE_POPULATIONS` and a file, and passive H with `OLD_POPULATIONS` each stop with status 70 and their message; passive He with `LTE_POPULATIONS` and active Ca II with `LTE_POPULATIONS` and a file run; He active writes `pops.HE.out`, He passive reads it with `OLD_POPULATIONS` and its spectrum differs from the LTE one. On a build of c204d76 the four refusal checks fail (those inputs run).

The manual (`docs/rhmanual.pdf`, §4.2.1) has an example `atoms.input` with Si PASSIVE `ZERO_RADIATION`, which now stops; the PDF is not changed here.
