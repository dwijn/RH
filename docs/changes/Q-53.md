title: Every allocation is checked: a failed one aborts with the routine, the size and the expression, instead of a segmentation fault (results unchanged)

The library made about 600 allocation calls, and about a dozen tested the result. A failed `matrix_*` allocation exited with status 70; any other returned NULL, and the run died of a segmentation fault without a message.

Now, as decided for phase 3, every allocation goes through a checked helper: `mallocOrAbort`, `callocOrAbort`, `reallocOrAbort` and `strdupOrAbort` (macros in the new `alloc.h`, which `rh.h` includes). On a failure they print the routine, the number of bytes and the size expression to stderr, and abort:

    -OUT_OF_MEMORY in routine readAtom
     Could not allocate 8589934592 bytes (Nlevel * sizeof(double))
     Aborting.....

The matrix allocators abort the same way. A zero size that gives NULL is not a failure. A script converted 492 calls (generated commit, in `.git-blame-ignore-revs`), and an independent check shows the code is otherwise unchanged token for token. Left alone: 13 allocations whose result the code already tests (they will return `RH_E_NOMEM` when their module is converted), and the helpers and the matrix allocators themselves.

This is the interim step. With phase 4, which gives the data owners (model, atmosphere, solver workspace) and their free paths, every allocation that can fail returns `RH_E_NOMEM`; the large setup arrays do so earlier, as their modules are converted to errors that return. The new unit test `test_alloc` checks the helpers and the abort, with its message, in a child process.

Phase 3 of the library track (`docs/LIBRARY.md` §6.3). Scripts and logs: `claude/RH/evidence/lib-q53-alloc`.
