title: solveray (2-D, 3-D) checks the direction cosines and clamps the derived one instead of returning NaN

`rhsc2d/solveray.c` and `rhsc3d/solveray.c` read two direction cosines from `ray.input` and computed the third as `sqrt(1 - (a² + b²))` without any check. When the squares summed to just over 1 (one input rounded up, e.g. `mux` written to 10 decimals, or FMA contraction on arm64) the root was a NaN and the run completed normally: in 2-D `muy` only enters `Bproject()`, so all polarized output at the line wavelengths was NaN while the continuum stayed finite; in 3-D `muz` itself was NaN (a crash in the formal solver). The separate range checks of each cosine let `mux = muz = 0.9` through. The 3-D `muy` message also named the interval `<0.0, 1.0>` for a check of `(-1, 1)`.

2-D: `muy = sqrt(fmax(0, 1 - sumsq))`, an error stating both cosines and the sum when `sumsq > 1 + 10⁻⁹`. The tolerance covers inputs rounded to 10 decimals (excess up to 3×10⁻¹⁰); `muy = 0`, a ray in the x-z plane, is valid. 3-D: `muz` divides the grid spacing in the stencil distances (`rz = muz/dz`, `dz/muz`), so `muz = 0` is not a ray: an error when `sumsq >= 1`, no clamp. Tested by `tests/e2e/solveray_cosines.py` (2-D: `mux = 0.8541662602`, `muz = 0.52`, sum 1 + 6×10⁻¹¹, was all NaN, now finite and equal to the ray with `mux` rounded down to 1×10⁻⁴ of the peak, the difference being muy = 0 against 5×10⁻⁶; 3-D: sum 1 + 3×10⁻¹¹ and `muz = 0` give errors, the old build crashed). Results do not change for valid rays (2-D and 3-D `solveray` output byte-identical to the base). Same code upstream (c95bdf6).
