title: rhsc2d: the Eddington approximation is selected with ANGLE_SET = SET_EDDINGTON again; what it cannot treat stops at input

`rhsc2d` has an Eddington mode: `Feautrier_2D` (`rhsc2d/formal.c`) solves each column on its own (1.5-D: no horizontal transfer) with one ray at mu = 1/sqrt(3), weight 1, including the diagonal operator, and `fillMesh()` returns early in that mode (no stencils). It was selected by the boolean keyword `EDDINGTON` until upstream commit df4c38f (2022-06-21, "Implemented Gauss-Lobatto quadrature"), which removed the keyword, added `ANGLE_SET = SET_EDDINGTON` (the `atmos.h` enum and `readvalue.c`) and implemented it in `rhf1d` only (`readinput.c`, `ONE_D_PLANE`; `rhf1d/anglequad.c`). Since then `input.Eddington` was never set (`formal2d`, `solve2d` and `formal3d` set it FALSE), so the 2-D Eddington branches were dead code, `ANGLE_SET = SET_EDDINGTON` in 2-D stopped in `getAngleQuadr` with "Did not recognize angleset", and `readinput.c` still warned about the old keyword. Upstream has the same dead branches. This change restores the mode through the angle set (Han's change looks like an oversight; the decision is the user's).

`input.Eddington` is removed (field and the three assignments). `rhsc2d` tests `atmos.angleSet.set == SET_EDDINGTON` in `fillMesh` (`geometry.c`) and `Formal` (`formal.c`); `getAngleQuadr` (`rhsc2d/anglequad.c`) gets a `SET_EDDINGTON` case with `Nrays = 1`, mux = muy = muz = 1/sqrt(3), weight 1 (the `SET_VERTICAL` case loses its `if (input.Eddington)`). `readInput` accepts `SET_EDDINGTON` in `TWO_D_PLANE` and treats NRAYS through one helper shared with the 1-D case (`setEddingtonNrays`: a value other than 0 or 1 gets the warning and NRAYS = 1; the 1-D message had a garbled line break and a different condition, now fixed); the old warning text is gone.

What `SET_EDDINGTON` cannot treat is everything for which `Formal` takes its angle-dependent branch (`angle_dep`: polarized active lines, polarized background lines, background polarization, angle-dependent PRD, or a moving atmosphere with lines at the wavelength), because that branch is the short-characteristics solver and `fillMesh` made no stencils for it: it would have used unallocated stencils. Each is now refused with `ERROR_LEVEL_2` (status 70) at the earliest point where it is known:

- `readInput` (`readinput.c`): 3-D plane geometry (`THREE_D_PLANE`: there is no 3-D Eddington solver; the 3-D angle quadrature already rejected it, now it stops at input with a message that says so). `SPHERICAL_SYMMETRIC` ignores `ANGLE_SET` with a warning, as for every value. The keyword-level refusals are not here: `readInput` is shared with `rhsc2d_solveray`, which switches the angle set to `SET_VERTICAL` and can solve a polarized ray.
- `checkEddington()` (new, `rhsc2d/geometry.c`; called once in `rhsc2d.c` and once in `gcheck.c`, right after `Background()`, when the atoms, the atmosphere and the background flags are all known). It scans what makes `angle_dep` true in `Formal`: `BACKGROUND_POLARIZATION = TRUE`; any magnetic field (`atmos.Stokes`: it makes the active lines polarizable whatever `STOKES_MODE` is, and `adjustStokesMode` turns `FIELD_FREE` into `FULL_STOKES` for the final solution, so a field-free setting would only have postponed the failure); polarized background lines (`backgrflags[].ispolarized`, any wavelength); `PRD_ANGLE_DEP = PRD_ANGLE_DEP` or `PRD_ANGLE_APPROX` with a PRD line (`NPRDactive > 0`; the keyword alone is harmless without one); a moving atmosphere with active atom lines or active molecules, or with background lines at any wavelength (`backgrflags[].hasline`, so a moving atmosphere with only Kurucz lines stops at setup, before the iterations).
- `Formal` (`rhsc2d/formal.c`): the same conditions per wavelength, naming the wavelength and the reason, as a backstop for anything `checkEddington()` misses (no known route reaches it).
- `chartflow` stops after reading the atmosphere (it analyses the short characteristics that this mode does not make); `formal2d` and `solve2d` (stand-alone formal-solution tools that read the angle set from their input) stop when given `SET_EDDINGTON`.
- `solveray` handles it: it solves its own ray with the short characteristics whatever angle set the main run used (J and populations come from `OLD_J`), so it switches the angle set to `SET_VERTICAL` after reading the atmosphere (the ray directions are redefined from `ray.input` anyway).

`Jgas` in the Eddington branch: that branch called `addJgasRow` for `PRD_ANGLE_APPROX`, although `PRD_ANGLE_APPROX` makes `angle_dep` true at the wavelengths of a PRD line. The call is reachable only with `PRD_ANGLE_APPROX` and a PRD line elsewhere in the spectrum (continuum or other-line wavelengths take the angle-independent branch), but that combination is now refused by `checkEddington()` since the PRD-line wavelengths could not be solved. The call can therefore never run and is removed (the comment in the branch says why). No angle-dependent Eddington solver is invented.

`LIMIT_MEMORY = TRUE`: the Eddington branch first accumulated into `spectrum.J[nspect]` directly, which is not allocated with `LIMIT_MEMORY` (J is a local buffer then, written by `writeJlambda`), so it crashed (reproduced: segmentation fault, CRD Ca II, 3 iterations); it now accumulates into `J[k]` like the short-characteristics branch, so `dJmax` and `writeJlambda` are right too.

Tests: the new e2e test `tests/e2e/eddington_2d.py` (`e2e_eddington_2d`, 16 s). FAL-C with Ca II (PRD) on the shipped 3-column `FALC_03x82.atmos`, `SET_EDDINGTON`: (1) converges (156 iterations to `ITER_LIMIT = 1e-4`), and the three identical columns give the same J and emergent I (difference exactly 0, required). (2) Against `rhf1d` with `SET_EDDINGTON` (one ray at mu = 1/sqrt(3) too, to `ITER_LIMIT = 1e-6`, 91 iterations): both are one ray at the same mu but the 1-D solver is DELO-Bezier and the 2-D one Feautrier on 82 depths, so they agree to discretization error: emergent I differs by 0.41% (median over the 287 wavelengths) and by 1.8% at most from 300 nm on (the Ca II K core, at 393.38 nm); below 150 nm, where the grid's optical depth steps are large and I is tiny, by 6.0% (median); J relative to its peak over depth by 0.27% at most from 300 nm on and 11% at most below 150 nm. At 125 nm, a deep minimum of I (7e-16 against a neighbouring 1e-14), the difference is 21 to 54% depending on the convergence, so the test bounds no worst case below 150 nm. A wrong mu would show: I of `rhf1d` with `SET_VERTICAL` differs from the Eddington one by 12.5% (median, from 300 nm). The test bounds are 1%, 3%, 15% (median below 150 nm), 1% and 15%. (3) Column independence: an atmosphere with ne of the columns scaled by 1, 1.3 and 0.7 gives, for every column, J and I identical (difference 0) to the run with that column's atmosphere in all three columns (10 iterations of `SOLVER = NG` without acceleration; the default `ANDERSON` and Ng acceleration couple the points, and scaling T instead would change the line wavelength grids, which follow the largest Doppler width of the atmosphere). (3b) `LIMIT_MEMORY = TRUE` gives the same `J.dat` and `spectrum.out` as FALSE to the bit (CRD Ca II; segmentation fault before the fix). (4) `solveray` after an Eddington run gives finite I, equal in every column; `solveray` with `SET_EDDINGTON` and a magnetic field in its `keyword.input` is not refused and runs. (5) The refused combinations (background polarization, magnetic field, `PRD_ANGLE_APPROX` and `PRD_ANGLE_DEP` with Ca II PRD, a moving atmosphere with active lines, a moving atmosphere with only a Kurucz line list (`checkEddington`, background flags), 3-D geometry, `chartflow`) stop with status 70 and the message of each. On the base commit (57acf33, the same sources apart from docs as c9154c0) the 2-D `SET_EDDINGTON` run stops with "Did not recognize angleset" (status 70), so the run checks fail, and each of the eight refusal checks fails (the message differs; for the input-level refusals the run used to stop at the same place with another message).

Results: no existing case changes. `SET_EDDINGTON` was not selectable in 2-D before and no shipped input uses it; every other path through the changed files is the same code. `tests/run_tests.sh --exact` against the base build is byte-identical for all cases.

The keyword value is documented in the `ANGLE_SET` comment of `rhsc2d/run/keyword.input` (the manual, `docs/rhmanual.pdf`, is not changed). Also present upstream.
